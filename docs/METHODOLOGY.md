# Методика MoneyGraph 1.0

## Наблюдения и гипотезы

Наблюдаются клиенты, направленные переводы, даты и суммы внутри ограниченной выборки. Не наблюдаются принадлежность к группе, полномочия, остатки, межбанк, переводы ниже порога и полная история. Аналитические признаки описывают сеть и помогают назначить проверку; они не устанавливают роль человека в реальной организации.

Три оценки не смешиваются:

- **Роль**: какой структурный/временной паттерн найден.
- **role_score**: насколько сильны признаки по прозрачной эвристике; не калиброванная вероятность.
- **priority_score**: кого проверять первым по связи с seed, охвату, объёму и положению в сети.

Граничный узел может иметь высокий приоритет и слабую определённость роли одновременно. Приоритет не умножается на уверенность: это не позволило бы заметить важные, но неполно наблюдаемые узлы.

## Входной контракт

Проверки реализованы обычными исключениями, а не `assert`, поэтому не отключаются при `python -O`.

1. Обязательные колонки присутствуют, не содержат пропусков.
2. ID целочисленные, входят в int64; преобразование из float запрещено как потенциально необратимое округление.
3. `gid` и агрегированные пары `(src,dst)` уникальны; все концы рёбер известны.
4. Суммы положительны и конечны; `n_tx` положителен; транзакции не ниже порога.
5. `is_seed` — bool, согласован с нулевой глубиной. Глубины в заданном диапазоне.
6. Даты без внутридневного времени находятся внутри периода.
7. Сверяются множества пар, суммы с абсолютным допуском 0.01 KZT и точное число операций.

Строки транзакций с совпадающими src/dst/date/sum остаются отдельными наблюдениями. Удалять их без ID операции нельзя. Узлы добавляются в граф **до** рёбер.

## Базовые признаки

`in_deg/out_deg` — число разных контрагентов; `in_tx/out_tx` — число операций; `in_kzt/out_kzt` — суммы, которые видны в графе. `pass_through = out_kzt/in_kzt` при положительном входе; иначе отсутствующее значение, не ноль.

`truncated_by_depth = (depth==4 AND out_deg==0)`. Такой узел не допускается к `terminal`, `transit`, `coordinator`. Входящие связи могут поддержать `consolidator`; его score на границе ограничен 0.60.

`balance_incomplete` отмечает seed либо превышение наблюдаемого выхода над входом. Даже при отсутствии флага полный баланс неизвестен. Числа, похожие на нормальный баланс, не доказывают полноту.

`seed_reach` — число разных seed, из которых существует ориентированный путь длиной 1–4 до узла; узел не считается собственным seed-предком. Отдельно есть число непосредственных seed-плательщиков. Это **не атрибуция всех денег** данного узла исходным seed и не соблюдение дат вдоль всей цепочки.

`betweenness` — нормализованное ориентированное посредничество на кратчайших путях по числу рёбер. `betweenness_pct` — эмпирический процентиль среди строго положительных значений с усреднением рангов при равенстве. Веса в деньгах не являются расстояниями.

`external_clusters` — число разных кластеров соседей, отличных от собственного, независимо от направления; на исходном графе дополнительно требуются входящие и исходящие связи. `reciprocal_neighbors` показывает двусторонних контрагентов; это не доказательство возврата тех же денег. Произвольные циклы и повторяющиеся временные маршруты в MVP не ищутся.

## Временное сопоставление

Точность исходного времени — день. Нельзя утверждать, что перевод B→C в ту же дату произошёл после A→B.

Для каждого узла:

1. Сгруппировать вход и выход по дню в целых тиынах (округление суммы ×100).
2. Хранить FIFO-очередь неизрасходованных входящих сумм.
3. Перед исходящими дня удалить из очереди поступления старше двух дней.
4. Сопоставить исходящие со входящими **предыдущих** 1–2 дней, уменьшая доступные суммы. Один вход не расходуется дважды.
5. После исходящих добавить вход текущего дня. Совпадение дат не становится подтверждением последовательности.
6. Для доли использовать только вход до `period_end - 2 дня`, чтобы у каждого входа было полное окно наблюдения. Соответствующее сопоставленное количество делится на этот вход.

`fast_1_2d_share` — совместимость сумм и дат **при предположении FIFO**. Смешение средств, остаток и внешние операции неизвестны; это не доказанный сквозной денежный поток и не общий баланс. Исключение последних двух дней не устраняет левое цензурирование начала месяца.

Дополнительно считаются число активных дней, максимальное число разных входящих плательщиков за день, доля оборота пикового дня и наличие позднего входа. Эти показатели доступны в JSON/CSV; в приоритете используется только FIFO-доля.

## Формулы силы признаков

Сначала проверяется допуск из README. Только допущенная роль получает score. Ниже `min(x,1)` обозначено `cap(x)`.

```text
consolidator = 0.50 + 0.35*cap(in_deg/12) + 0.15*cap(seed_reach/4)
distributor  = 0.55 + 0.45*cap(out_deg/60)
transit      = 0.50 + 0.25*(1-abs(1-pass_through)) + 0.25*fast_1_2d_share
terminal     = 0.50 + 0.20*(1-pass_through/max(terminal_ratio_max, 1e-9))
coordinator  = 0.55 + 0.20*cap(seed_reach/5) + 0.25*betweenness_pct
```

`terminal` ограничен 0.70, поскольку полное удержание денег не наблюдается. На границе положительная гипотеза ограничена 0.60. `peripheral` получает 0.15 при изоляции/обрыве и 0.35 в остальных случаях — это слабость доступных свидетельств, а не вероятность отсутствия роли.

Если допущен `coordinator`, он основной; остальные сохраняются как альтернативы. Иначе основной — максимальный score. При точном равенстве порядок: `consolidator`, `distributor`, `transit`, `terminal`. Ни один конкретный gid в правилах не указан.

Пороги 3/10, интервалы отношения и веса — стартовые эвристики MVP. Они документированы и настраиваются через JSON, но не оптимизированы по неизвестной разметке. Ограничение `coordinator` по кластерам делает эту роль чувствительной к resolution Louvain.

## Приоритет

Формула в README. Все шесть слагаемых экспортируются отдельными колонками `priority_seed`, `priority_collection`, `priority_volume`, `priority_bridge`, `priority_distribution`, `priority_temporal`.

`S(x)` использует P95 **положительных значений** и log1p; это уменьшает влияние редких крупных значений, но вызывает насыщение. Нулевые признаки остаются нулями. Приоритет округляется до шести знаков, затем ties разрешаются по числовому gid. Стабильный tie-break — технический порядок, не дополнительный сигнал риска.

Маленькие компоненты не отбрасываются, но глобальное нормирование может снижать их позиции. Аналитик должен дополнительно просматривать лидеров каждого кластера. Признаки высокой связности могут относиться к легальным массовым получателям; клиентских атрибутов для их отличения нет.

## Кластеры

Неориентированная проекция применяется только для сообществ; направления сохраняются во всех финансовых метриках и интерфейсе. Вес пары — `log1p(sum(A→B)+sum(B→A))`. Это не сумма логарифмов. Самопетли пропускаются в проекции, но исходные операции не удаляются.

Louvain запускается для каждой слабосвязной компоненты с `resolution=1`, `seed=42`. Итоговые группы сортируются по убыванию размера, затем минимальному числовому gid. Повторный запуск на тех же данных с теми же версиями даёт одинаковые ID. При изменении данных ID кластеров могут измениться; это не постоянные идентификаторы групп.

Гипотеза кластера — шаблон из фактически посчитанных ролей и числа seed. Приложение не выдумывает назначение вроде «оптовая торговля» без подтверждающих данных.

## Исключение узлов

Для топ-1/3/5 сравнивается число направленно достижимых пар `(seed, node)` в пределах четырёх рёбер до и после удаления. В обоих состояниях сравниваются только **сохранившиеся** конечные узлы и seed, чтобы не выдавать простое удаление самого клиента за разрыв чужих маршрутов. Отдельно сохраняются число удалённых seed, новые компоненты и размер крупнейшей.

Это статический сценарий на наблюдаемом графе. Он не моделирует восстановление инфраструктуры, альтернативные внешние счета, реакцию участников или юридический эффект блокировки.

## Проверка качества без ground truth

- Контрактные проверки и синтетические контрпримеры подтверждают выполнение заявленной логики.
- Повторный запуск и перемешивание строк проверяют воспроизводимость.
- По произвольному gid объяснение должно восстанавливаться из CSV, порогов и слагаемых.
- Для следующей версии: сравнить топ-20 при изменении порогов ±20%, resolution 0.8/1.0/1.2; измерить пересечение топов и изменение ролей. Высокая устойчивость не заменяет истинную разметку.
- Для реальной эксплуатации нужны экспертная проверка кейсов, отрицательные примеры легальных сетей и оценка ложных срабатываний. Таких результатов у MVP нет.
