# Как команде получить и защитить MVP

Основной MVP уже реализован. Сначала воспроизведите его, затем решайте, какие дополнения успеете защитить.

## Первые 20 минут

1. Получить исходники проекта и открыть папку с `run.py`.
2. Создать Python 3.12 окружение и установить `requirements.txt`.
3. Распаковать оригинальный архив данных: три Parquet должны находиться непосредственно в `data/`.
4. Выполнить `python run.py --data data --out results --serve --open` через Python своего окружения.
5. Убедиться в наличии 2 248 узлов; найти произвольный gid, открыть его связи и объяснение.
6. В другом терминале: `python -m unittest discover -s tests -v`, затем `python scripts/check_submission.py --data data --out results`.
7. Перенести исходники в ветку GitHub и проверить GitHub Actions. Реальные данные не включать в публичные CI-артефакты.

## План на оставшиеся часы хакатона

| Время | Работа | Проверяемый результат |
|---|---|---|
| 0:00–0:30 | Совместный запуск и разбор ограничений | У каждого работает расчёт, понятна ловушка четвёртого колена |
| 0:30–1:30 | Аналитик команды проверяет 6–10 разных карточек; разработчик осваивает код | Обоснованные критерии, список спорных гипотез |
| 1:30–2:30 | Улучшить один полезный сценарий: устойчивость порогов или временные маршруты | Измеримый результат с объяснением, без поломки контрактов |
| 2:30–3:30 | Интерфейс и демонстрация на произвольном gid | Поиск, стрелки, роли, кластеры, ограничения читаются быстро |
| 3:30–4:15 | Проверить запуск на второй машине/чистом окружении | Три CSV, время <5 минут, все тесты проходят |
| 4:15–5:00 | Freeze, README, репетиция защиты | Репозиторий, схема, результаты и демо на 5 минут |

## Роли в команде из 3–4 человек

- Аналитика: проверить допуски ролей, отличия `role_score`/`priority_score`, объяснения выбранных примеров.
- Пайплайн: контракты, тесты, временные признаки, замеры и воспроизводимость.
- Интерфейс: удобство обзора подграфов, поиск, подсказки и читаемость.
- Презентация/интеграция: README, PR, чистый запуск, сценарий защиты. При трёх участниках совместить с аналитикой.

Разделяйте файлы между участниками, чтобы не менять один HTML одновременно. Любая новая метрика должна попасть в описание метода и обоснование узла, иначе на защите её трудно объяснить.

## Что не делать до сдачи

- Не заменять работающие правила необъяснимой моделью без размеченных ролей.
- Не добавлять облако/LLM в обязательный путь расчёта.
- Не подбирать конкретные gid как «правильный ответ».
- Не добиваться ровно восьми кластеров: число не является контрактом.
- Не удалять изолированные seed или одинаковые строки транзакций ради красивой статистики.
- Не называть топ-лист доказательством виновности или прогнозом предотвращённого ущерба.

## Критерий готовности

Одна команда создаёт три обязательных CSV, интерфейс находит любой gid, все 2 248 узлов представлены, у каждого непустое числовое объяснение, `terminal` не назначается обрезанным узлам, жюри может повторить запуск. Только после этого добавляйте необязательные возможности.
